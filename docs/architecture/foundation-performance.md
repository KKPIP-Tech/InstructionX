# Task 10 性能优化与对照证据

## 1. 测量口径

- 优化前：`temp/foundation-baseline.json`
- 优化后：`temp/foundation-optimized.json`
- 同一 Windows 11 机器、CPython 3.14.3、24 逻辑核心，脚本与固定数据规模一致。
- 批量场景：12 轮，每轮 100 键，每键 1024 字节；优化前回退为逐键写入，优化后使用单事务 API。
- 每个指标均保留原始样本、p50/p95/p99、最大值和样本数。单次生命周期测量不能证明稳定分布。
- 真实 GUI、外部 Provider 网络、物理磁盘满和 长稳负载不在本报告验收范围内。

Task 0 的原始 JSON 在当前 `temp/` 中已不存在，因此本报告使用 Task 9 完成后、Task 10 修改前重新采集的基线，不虚构与历史提交的比较。

## 3. 模型刷新与脱敏开销

Task 10 曾让 `refresh_all_models()` 复用 ProviderSupervisor 并行刷新并增加总截止期。后续实际使用发现并行缓存写会产生共享 `.tmp` 冲突和缓存合并风险，且典型用户只有一到两个常用模型，并行收益不成立。当前已回退为按注册顺序逐个刷新、单 worker 顺序写缓存；`force` 与 `timeout` 参数保持可调用，`timeout` 不再表示并行总截止期。受控测试验证刷新不重叠、启动顺序、单 Provider 故障隔离和真实健康状态。

脱敏正则由“每次日志/标签重新编译”改为缓存，只有注册新的敏感字段时失效。新增字段在缓存建立后仍立即生效，不以性能为由减少脱敏范围。

## 4. 未修改项

常规 SQLite、事件和纯算法图表指标均在 SLO 内，没有 profile 证明 UIKit 需要改动，因此继续使用既有环形缓冲、帧合并、采样金字塔和 GL/软件回退，不做盲目调参。

## 5. 正确性与完整比较结论

- 故障矩阵、数据层和性能契约：114/114 通过。
- 可观测性与性能缓存专项：18/18 通过。
- 全量 pytest：1311/1311 通过，只有既有 6 个 GBK 警告。
- 最新比较给出 11 项改善、5 项回归，因此 `comparison.status=REGRESSION`，不能写成“全面零回归”。回归项是 Provider 恢复微秒值、长期任务注册、事件发布、MCP 停止和点查等非目标路径；重复采集的回归项会变化，不能把波动直接归因于批量或并行刷新改动，也不能据此宣称噪声已经被排除。
- 数据库锁定、只读、模拟磁盘满和旧同步慢订阅者仍是后续 Task 11 的故障处理对象；真实 GUI、外部网络、物理磁盘满和 长稳负载仍为 NOT_RUN。

本报告只确认目标优化具有显著收益、对应 SLO 通过且正确性测试无回归，不把单次比较器状态或局部优化包装成整个框架已经满足全部工业/医疗验收。
